How we work with agents

Agents are teammates, not magic: they go through the same doors we do, and every change — human or agent — faces the same gates. This page is the map. The depth belongs in your repo, next to the code it describes.

Replace this page. Everything below is a plausible default, not advice about your codebase. The parts worth keeping are the shapes — one gate, a ticket lifecycle, a proof convention — not the specifics.

The shape of a change

Whatever the tool, useful agent work tends to have the same spine. Naming it out loud is most of the value of a page like this.

What the agent decides

How to implement it. Which files to touch. What to name things. Where the seams go. You will get better results arguing about the acceptance line than about the diff.

What you decide

Whether the ticket is worth doing, whether the acceptance line is honest, and whether the proof convinces you. Those three do not delegate well.

One gate, not a checklist

The single highest-leverage thing you can give an agent is one command that says yes or no. Not a wiki page of steps — one command, exit code 0 or not.

./check          # or: make check, npm test, cargo test, ./gradlew check

It matters that it is one command because:

  • An agent can run it. A checklist in a doc is something an agent claims to have followed. A command is something it either passed or did not.
  • It is the same gate for everyone. If CI runs something the local command does not, the local command is a lie and people stop trusting it.
  • It names what it proved. Have it print the commit it checked. "Tests pass" is a claim about a moment, and the moment moves.
Green means proven, not finished. A gate says the change did not break what you already knew to check. Whether it did the thing the ticket asked is a question for the proof below.

The board is the interface

If the dashboard's agent queue is going to work, tickets have to carry enough to act on. The convention this hub ships with is one line:

Done = the save file survives a restart and reloads to the same state

A ticket with a Done = line is an agent-ready spec, and scripts/fetch-data.mjs filters the queue on exactly that. Tickets without one simply do not appear — which is what gives writing the line a point.

  1. To Do — has a title. May or may not have an acceptance line.
  2. Agent-ready — has Done =. Shows up in the queue on the Dashboard.
  3. In Progress — set when work starts, not when it finishes. A board that only updates at the end is a board nobody trusts mid-week.
  4. In Review — a PR exists and its link is on the ticket.
  5. Done — merged.

The board stays truthful as a byproduct of the work rather than as a separate chore. That only holds if the agent updates it as part of the same session — which is why the prompt templates in hub.config.js say so explicitly.

Proof beats description

The failure mode of agent work is a confident summary of something that did not happen. The fix is cheap: make the PR carry evidence a human can check in ten seconds.

Mechanical proof

The gate output, pasted. A test that was red and is now green. A number that moved. Anything reproducible by someone who does not trust you.

Visible proof

A screenshot or a short capture in the PR body — before and after where it makes sense. Upload it to the hub as well and it shows up on the Dashboard for the whole team.

Rules of the road

  • Brief the repo, not the session. An AGENTS.md at the root loads automatically for most agents. Anything you find yourself re-explaining belongs there.
  • Quote every path with a space in it. This costs one character and saves an hour roughly once a month.
  • One ticket, one branch, one PR. A branch that grows a second purpose stops being reviewable.
  • Read the diff. Not the summary of the diff. This is the whole job now.
  • If the gate is wrong, fix the gate. Working around a false failure teaches everyone that red is negotiable.

Writing your version of this page

The useful version of this page is short, opinionated, and specific to things a newcomer would otherwise get wrong. Some prompts:

  • What is the one command that proves a change is safe?
  • What does an agent need to know that is not obvious from reading the code?
  • What has actually gone wrong twice? That is a rule, not a footnote.
  • Where does the deep documentation live, so this page can stay a map rather than a fork of it?
Keep it a map. The moment this page starts duplicating documentation that lives in the repo, it starts going stale — and a stale guide is worse than no guide, because people believe it.
